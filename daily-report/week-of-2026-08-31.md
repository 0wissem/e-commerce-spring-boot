## Monday 2026-08-31 — Dev-DB cleanup, cold-call drilling, then optimistic locking

### What I did

- **Cleaned the verification data out of the dev databases** left over from the enrichment week —
  one admin user, two products, three orders. Inspected the full tables before deleting rather than
  pattern-matching, because those databases also hold older test data and my own account. Deletes
  were scoped by exact id, run in transactions, children before parents. Hard deletes, not soft:
  product-service uses `@SQLRestriction("deleted_at IS NULL")`, so stamping `deletedAt` would have
  hidden the rows while leaving them in the table.

- **Ran a cold-call drill** rather than re-reading notes. Graded blocks: expand/contract and why a
  one-shot `ALTER TYPE` is unsafe (**15/20** after correction), the proxy/self-invocation rule
  (**16/20**), `@Component` vs `@Bean` (**14/20**), `@RequestParam` vs `@PathVariable` (**18/20**),
  `ResponseEntity` vs my `ApiResponse` envelope (**20/20** on the retry). Weak spots that need
  re-drilling: **IoC vs DI as separate ideas** (9/20 — I described the effect, "less boilerplate",
  not the principle), **DTO reasons** (11/20 — got security, missed coupling), **`@Valid`**
  (12/20 — said "checks types", it checks *constraints*, and the exception is
  `MethodArgumentNotValidException`).

- **The instructive miss: I applied the self-invocation rule correctly to `@Transactional`, then
  failed it thirty seconds later on `@Cacheable`.** `this::getById` inside a stream is the same
  proxy bypass. The knowledge was there; the *transfer* wasn't. The generalisation to hold is one
  rule, not six facts: `@Transactional`, `@Cacheable`, `@CacheEvict`, `@Async`, `@PreAuthorize`,
  `@Retryable` — all dead on a `this.` call.

- **Corrected a stuck mental model.** Three times I attributed the N+1 problem to EAGER fetching.
  My own `ProductNPlusOneTest` produces it with **LAZY** — that is the whole point of the test.
  Both can cause N+1; LAZY is preferred because it is fixable *per query* with `@EntityGraph`,
  where EAGER pays the cost on every read with no escape. Memory hook: **LAZY is the cause,
  EntityGraph is the cure.**

- **Added optimistic locking.** `@Version` on `Product`, backed by a `version` column. Every UPDATE
  becomes `... SET version = version + 1 WHERE id = ? AND version = ?`; if a concurrent transaction
  already bumped it, zero rows match and Hibernate raises `OptimisticLockException`. No lock is
  taken — conflicts are **detected** at write time, not **prevented** at read time.

- **Put the retry in a separate bean, deliberately.** When a conflict fires, that transaction is
  already marked rollback-only, so the retry must start a *fresh* one. A private method on
  `ProductService` could not do that: `@Transactional` is proxy-based, and an internal call opens
  no transaction at all. `StockService` calls through the injected proxy, so every attempt genuinely
  gets its own transaction. The morning's drill, cashed in the same afternoon.

### Problems and how I resolved them

- **Three retries was not enough, and the test proved it.** 20 threads racing for 10 units: only
  **6 succeeded instead of 10**. Four threads burned all three attempts and failed a decrement that
  should have worked. Under N-way contention on one row, an immediate retry collides with the same
  crowd that just beat it. Fixed with **exponential backoff plus full jitter** — the randomness is
  what matters, not the delay: a fixed wait just reconvenes the same herd one interval later. Same
  reasoning as jittering cache TTLs against a stampede.

- **My test swallowed the failure that would have told me this immediately.** A bare
  `catch (Exception e) {}` meant the counts were simply short with no visible cause. Now unexpected
  exceptions are collected and asserted on, so the *reason* surfaces instead of a bare mismatch.

### Key takeaways

- **Optimistic locking detects; it does not prevent.** That is why it needs a retry, and why the
  retry needs somewhere outside the failed transaction to live.
- **Retry without jitter is not a retry policy** — it is the same collision, rescheduled.
- **Knowing a rule and transferring it are different skills.** I applied the proxy rule and then
  missed it one question later on a different annotation.

## Tuesday 2026-09-01 — Pessimistic locking, deadlocks, and a measured comparison

### What I did

- **Implemented the pessimistic counterpart**: `findByIdForUpdate` with
  `@Lock(PESSIMISTIC_WRITE)` and a 3s lock timeout, issuing `SELECT ... FOR UPDATE`. The row is
  locked *before* it is read, so a second transaction blocks at the SELECT until the first commits
  and then reads the updated value. The conflict cannot occur, so **there is no retry loop at all**
  — that absence is the clearest contrast with Monday.

  ```
  optimistic  = read freely, fail at write, retry     → cheap when conflicts are rare
  pessimistic = queue at read, never fail, never retry → cheaper when they are common
  ```

- **Reproduced a real deadlock.** Thread 1 locks row A then B; thread 2 locks B then A. A cycle,
  and Postgres detects it and kills one victim with **SQLState 40P01** rather than hanging forever.
  Then proved the cure: when both threads take rows in the **same sorted order**, a cycle cannot
  form by construction — someone always gets both locks first and the other simply waits. This is
  not theoretical for us: a basket containing two products locks two rows, and two customers buying
  the same pair in opposite order is exactly that cycle.

- **Measured both strategies on the same workload.** 30 threads on one row:

  | strategy | time |
  |---|---|
  | optimistic (`@Version` + retry/backoff) | **649 ms** |
  | pessimistic (`SELECT ... FOR UPDATE`) | **116 ms** |

  5.6× — because under heavy contention the optimistic losers redo their transaction *and* sleep on
  backoff, while the pessimistic ones queue once and do the work exactly once. Under **low**
  contention the ranking reverses, since optimistic takes no lock at all.

### Problems and how I resolved them

- **A pessimistic lock requires a transaction, and the failure said so plainly:** "No active
  transaction". A lock lives for the length of a transaction; with none, there is nothing to hold it
  open, so Spring rejects the request rather than handing back an unlocked row and pretending.
  Turned that into an explicit test instead of hiding it — it is a genuine difference from
  `@Version`, which needs no transaction to *read* and only detects the conflict later.

- **Printed the benchmark rather than asserting on it.** Wall-clock timing on a shared machine is
  not a contract; turning an observation into an assertion is how a suite becomes flaky. The test
  asserts **correctness** (neither strategy oversells) and prints the timings.

### Key takeaways

- **Both strategies are correct; they differ in cost and in failure mode.** Choosing is about
  expected contention, not about which is "safer".
- **A deadlock needs a cycle, and consistent lock ordering makes cycles impossible.** Sorting the
  rows before locking is the entire fix.
- **Postgres breaks deadlocks for you** — it picks a victim, it does not hang. The bug is the cycle,
  not the hang.

## Wednesday 2026-09-02 — Transaction isolation, demonstrated rather than recited

### What I did

- **Reproduced each anomaly with two genuinely concurrent transactions** on real Postgres, driving
  them manually through `PlatformTransactionManager` so I could control exactly when each one reads,
  writes and commits. H2 could not do this — the anomalies depend on the engine's real MVCC.

- **Dirty read:** impossible in Postgres. Held an uncommitted write open on one connection and read
  from another at READ UNCOMMITTED — the change was invisible. Postgres implements READ UNCOMMITTED
  as READ COMMITTED, so the weakest anomaly cannot happen whatever you ask for.

- **Non-repeatable read:** at READ COMMITTED, the same row read twice in one transaction returned
  100 then 60, because a concurrent writer committed in between. At REPEATABLE READ the snapshot is
  pinned to the start of the transaction and both reads agree — stable, at the cost of reading data
  that is already stale.

- **Phantom read:** the same range query returning a row that did not exist before. Distinct from a
  non-repeatable read — that is an existing row *changing*, this is a new row *appearing*.

- **The detail worth carrying into an interview:** the SQL standard **permits** phantom reads at
  REPEATABLE READ and says you need SERIALIZABLE to stop them. Postgres implements REPEATABLE READ
  as true snapshot isolation, so phantoms cannot occur there either. Quoting the standard's table as
  if it described Postgres is a confident and common error.

- **Showed the declarative form too.** Everything above drives transactions by hand, which no
  application would do. Added a bean using `@Transactional(isolation = …)` and asserted, by asking
  the *server*, that the level really takes effect.

### Problems and how I resolved them

- **I asserted a label instead of a behaviour, and it was simply wrong.** My first dirty-read test
  checked that Postgres *reports* "read committed" when asked for READ UNCOMMITTED. It reports
  whichever level you asked for. Rewrote it to prove the behaviour with two connections and an
  uncommitted write — which is the actual claim worth making.

- **I wrote a fake helper and it made a test prove nothing.** `clearPersistenceContext()` was a
  no-op with a comment claiming otherwise, so the "second read" hit Hibernate's first-level cache
  and never reached the database. The test passed and demonstrated nothing until it called
  `em.clear()`. A green test with a misleading name is worse than no test.

### Key takeaways

- **Assert behaviour, not labels.** What a system *reports* and what it *does* are different
  claims, and only one of them is worth testing.
- **Postgres is stricter than the SQL standard at REPEATABLE READ.** Know the standard *and* the
  implementation; they disagree.
- **Hibernate's first-level cache will silently invalidate a concurrency test.** If the second read
  never issues SQL, the test is measuring nothing.

## Thursday 2026-09-03 — Transaction boundary, contract migrations, and two bugs on the live stack

### What I did

- **Removed the HTTP-in-transaction bug** — the flaw I had been volunteering in interviews for
  months. `OrderService.create()` was `@Transactional` and made every cross-service call inside that
  boundary, pinning a database connection for the whole round trip: connection-pool exhaustion
  waiting for load. The class-level annotation is gone; reads are `@Transactional(readOnly = true)`,
  and the single write is delegated to a separate `OrderPersister` bean so the call goes through a
  proxy. The transaction now covers one INSERT and opens only after every remote call has returned.

- **Parallelised the cross-service lookups** with `CompletableFuture` on a **dedicated** executor.
  Not `ForkJoinPool.commonPool()`: that is sized for CPU-bound work and shared by the whole JVM, so
  blocking it on network I/O starves everything else. Latency went from the *sum* of the round trips
  to the *max*.

- **Proved the boundary moved**, rather than claiming it. `OrderTransactionBoundaryTest` asks
  `TransactionSynchronizationManager` from inside the mocked client whether a transaction is active;
  the assertion is that **no remote call ever sees one**. Before the refactor that list would have
  contained every call.

- **Completed the money migration with the contract phase** — deliberately deferred for two weeks
  because that separation *is* the pattern. Done as three steps, not one:

  ```
  V7  DROP NOT NULL on price      <- both code versions still valid
      deploy: entity stops mapping the column
  V8  DROP COLUMN price
  ```

  Reversed, either order breaks: drop the column while an old instance still maps it and every
  INSERT fails; stop writing it while it is still NOT NULL and every INSERT fails for the opposite
  reason. The nullable step between them is what keeps both versions valid at once — V2 in reverse.
  Same shape in order-service (V5/V6) for three columns.

- **Deleted the deprecated shims and let the compiler find the rest.** Removing
  `Product.getPrice()`, `Order.getTotalPrice()` and friends surfaced seven remaining call sites
  immediately. That is the argument for `@Deprecated` shims over a big-bang rename: migrate
  incrementally, then delete and let `javac` prove nothing was missed.

- **Rebuilt and restarted the stack** to apply V6–V8 against databases holding real rows — not a
  fresh Testcontainers schema. All five migrations applied cleanly, `price` dropped, every amount
  intact, `version` defaulted to 0 on existing rows, and the API response was **unchanged**: the
  drop was invisible to clients.

- **Verified the whole point end to end:** 25 concurrent real orders against 10 units of stock →
  **10 created, 15 refused with 409, zero errors**, final stock 0, version +10.

### Problems and how I resolved them

- **Order creation was completely broken, and no test could see it.** order-service called the stock
  endpoint with **no Authorization header**, but everything except GET requires ADMIN — so every
  order died with a 403. The suite mocks `ProductServiceClient` entirely, so the *absence* of a
  header was invisible to it. Only a manual call against the running stack found it.

- **The fix exposed a sharper trap.** Forwarding the caller's JWT is not enough:
  `SecurityContextHolder` is a **ThreadLocal**, and the lookups now run on a separate pool where it
  is empty. Read it inside the async task and you get null, and the call still goes out anonymous.
  The token must be captured on the **request thread**, before the async hop, and passed down as a
  value. My own parallelisation created the trap the same day.

- **My error mapping was lying.** `onStatus(is4xxClientError, …)` turned *any* 4xx into "Product not
  found", so the 403 above reported as a 404 and sent me debugging the wrong service entirely. Now
  only 404 means not-found; other 4xx says what actually happened.

- **Then I proved the regression tests actually catch the bug.** I temporarily reverted the fix
  (`callerToken = null`) and re-ran: two of three went red. A regression test that passes both
  before and after the fix proves nothing — the same failure mode as the fake helper on Wednesday,
  so this time I checked instead of assuming.

### Key takeaways

- **Mocked clients cannot test the wire.** Auth headers, serialization, status codes — anything
  that only exists *between* services is invisible to a suite that mocks the boundary. That bug
  survived 101 green tests and took one manual call to find.
- **Parallelism silently drops the security context.** `SecurityContextHolder` is a ThreadLocal;
  capture what you need on the request thread before going async.
- **Never map a whole status class to one meaning.** "Any 4xx = not found" turned a permissions
  failure into a phantom missing product.
- **Verify a regression test by breaking the fix.** If it still passes, it is decoration.
- **The full expand/contract arc cost six deploys** to change one column's type with zero downtime
  and a live rollback path throughout. That is the real price of the pattern — and the reason you
  only pay it when the column matters. Money did.
