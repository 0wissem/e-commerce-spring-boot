## Monday 2026-07-27 — Learning-path review, then scaling the data layer: replicas, partitioning, sharding

### What I did

Phase 2 (Spring deep-dives) is effectively done in practice but was never ticked off in `BACKEND_LEARNING_PLAN.md`: bean lifecycle/DI (07-15), Spring Security / cross-service JWT (07-02), validation and global error handling (07-13) all happened in sessions but the progress log still ends at 2026-06-29. - **Opened with cold retrieval on last Monday's material** rather than re-reading it — the four metrics and their trade-offs, the honest version of CAP (partitions aren't optional, so the real choice is C *or* A), and the one that matters most: *my own system already made that choice.* The monolith and product-service hold separate databases, so a network split between them means the order-creation path can't fetch a product snapshot. I chose availability and eventual consistency the day I picked the snapshot over the join — I'd just never named it.

- **Built the scaling ladder as an ordered model**, because the order *is* the answer: (1) **vertical scaling** — bigger box, correct far longer than engineers admit, especially once the working set fits in RAM; (2) **read replicas** — scales reads only, since every replica still applies every write, and you buy it with **replication lag**; (3) **functional partitioning** — split by domain; (4) **horizontal sharding** — one table across N machines, the expensive and effectively irreversible rung. Jumping straight to "shard it" is the marked-down answer.

- **Realised rung 3 is something I have already shipped.** Splitting the monolith into monolith/product-service/order-service with one Postgres each *is* functional partitioning — "vertical sharding" in system-design vocabulary. And I've already paid its price: the moment products left the monolith, `orders JOIN products` stopped existing and became an HTTP call plus a JSONB snapshot. That's a claim I can now make concretely — I've scaled a data layer by domain and lost my joins doing it.

- **Worked the shard-key decision on `orders`**, the table that actually grows without bound (products are ~10k and capped). Three properties in tension: **even distribution**, **query locality**, and **stability** of the key.
  - `order_id` (hash) → perfect spread, but "show me my order history" doesn't know which shard holds the rows, so it fans out to all N and waits on the slowest. The dominant query becomes the slowest one.
  - `created_at` (range) → trivial to archive and rebalance, but **every insert lands on today's shard**. All writes on one machine — the planted wrong answer.
  - `customer_id` (hash) → one customer's history lives on one shard, so the dominant read is single-shard. Distribution is *nearly* even, with hot-shard risk from an outlier enterprise customer.
  - **Call: `customer_id`** — locality over perfect distribution, because the dominant access pattern is per-customer. The reasoning is the answer, not the key.

- **Listed what breaks after sharding:** cross-shard joins (reassemble in app code or denormalize), cross-shard transactions (no more single-DB ACID → sagas or 2PC), rebalancing (naive `mod N` remaps nearly every row → **consistent hashing** moves only ~1/N), and hot shards.

### What I'm planning

### Key takeaways

- **Sharding is the last rung, not the first.** Vertical → replicas → functional partitioning → horizontal sharding. Naming the order matters more than knowing the mechanics of the last rung.
- **Read replicas scale reads, never writes.** Every replica applies every write; the write ceiling is unchanged. What you're buying is throughput in exchange for staleness.
- **The shard key is the whole decision, and it's irreversible.** Even distribution, query locality, and stability pull against each other — you pick which to sacrifice, justified from the dominant access pattern.
- **I've already lived rung 3.** The Strangler Fig extraction was functional partitioning, and the JSONB snapshot was the bill for it.

## Tuesday 2026-07-28 — Database fundamentals: ACID, normalization, and the SQL vs NoSQL decision

### What I did

- **Closed the database block** that started Friday with indexing and B+trees, moving up from *how the storage works* to *what guarantees the database gives you*.
- **ACID, property by property** — Atomicity (all or nothing), Consistency (constraints hold before and after), Isolation (concurrent transactions don't see each other's partial work), Durability (committed means survives a crash). Tied straight back to `OrderTransactionalTest` in order-service, where I already proved atomicity: a mid-flight product-lookup failure rolls the whole order back, leaving no partial write.
- **Normalization and its deliberate reversal** — normal forms exist to remove duplication so one fact lives in one place and can't go inconsistent. Then the counter-move: **denormalization is a legitimate choice at scale**, because once you shard, joins across machines are expensive or impossible. My `OrderProductSnapshot` is exactly that — duplicated product data stored on purpose, so the order survives the product changing.
- **Foreign keys** — what the constraint actually enforces, and why cross-service references (order → product) *can't* be foreign keys once the two live in different databases. The integrity guarantee moves from the database to the application, which is a real cost of extraction that I'd paid without naming.
- **SQL vs NoSQL as a decision, not a preference** — relational when you need joins, transactions, and a stable schema; document/key-value when you need horizontal scale and flexible shape, at the cost of the guarantees above. The honest framing: NoSQL doesn't remove the work, it moves it into the application.

### Key takeaways

- **Normalization protects correctness; denormalization buys scale.** Both are right — the question is which failure you can afford.
- **A foreign key is a guarantee the database makes for you.** Cross a service boundary and you inherit that job yourself.
- **I already made these calls before I had the vocabulary.** The snapshot is denormalization; the missing FK is the price of the split.

## Wednesday 2026-07-29 — API design, real-time delivery, and the start of AWS SAA prep

### What I did

- **Worked API design as a set of decisions:** REST resource modelling, **versioning** strategies, **pagination** (tying back to keyset vs offset from 07-24), **idempotency keys** on unsafe operations (the same at-least-once problem from Friday, solved at the API edge), consistent **error shapes**, and where **GraphQL** genuinely helps versus adds cost.
- **Nailed 401 vs 403** — 401 *unauthenticated* (I don't know who you are; the token is missing, expired, or invalid) versus 403 *authenticated but unauthorized* (I know who you are and you still can't). Directly relevant to the gateway's JWT filter, where getting this wrong sends the frontend into a pointless re-login loop.
- **Real-time delivery, three options:** short/long **polling** (simple, wasteful), **WebSocket** (bidirectional, persistent, stateful — which is exactly what makes load balancing harder), and **SSE** (server→client only, over plain HTTP, far simpler when you don't need the upstream channel). The decision rule: pick the weakest mechanism that does the job.
- **Started AWS Solutions Architect Associate prep** as a second, deliberately smaller thread — the aim being to bridge each system-design answer to "and which AWS service is that."

### Problems and how I resolved them

- **The first AWS pass was a term-dump and it did not work.** Ten services and their acronyms in one go — I got overwhelmed and demoralized, and said so plainly: *"I don't have a memory card, I forget 70%."* The instinct to blame my memory was wrong; the **format** was the blocker, the same one I'd flagged on Monday.
- **Fixed it with one vivid picture per service, one at a time, short.** SQS = a 🟠 **mailbox** (one letter, one reader). SNS = a 📻 **radio tower** (shout once, everyone hears). Kinesis = a 🟢 **river** (a live flood you can watch and rewind). S3 = a 📦 **giant warehouse** (dump big files, keep the link in the DB). EC2 = a 🖥️ **bare rented apartment** (you set it all up, it runs 24/7). Elastic Beanstalk = a 🛠️ **furnished, move-in-ready apartment** sitting on top of EC2. Lambda = a ⚡ **vending machine** (runs only when triggered, pay per press). Concrete images stick where acronyms slide off.

### Key takeaways

- **Pick the weakest real-time mechanism that satisfies the requirement** — SSE over WebSocket whenever the channel is one-way.
- **401 is "who are you", 403 is "not you".** Cheap to confuse, expensive in the client.

## Thursday 2026-07-30 — Cold recall proves the method; distributed-systems patterns

### What I did

- **Cold-tested the AWS pictures after a full day's gap — 5/5 recalled**, unprompted, by their image. That settled the question from Wednesday: my memory was never the problem. One vivid picture per concept, spaced overnight, works; dense lists do not. Extended the deck toward the wider service catalog on the same pattern.
- **Made an explicit balance decision:** AWS service memorization is **one thread, not the main course**. Left unchecked it crowds out the actual architect skill. The rule going forward — center each session on **system-design reasoning** (trade-offs, sharding, caching, fan-out) and the parked backend drills, then weave AWS in as the "which service implements this" bridge, a few pictures at a time.
- **Distributed lock** — why "check then act" across N instances is a race, and the Redis `SET key value NX EX ttl` primitive as the standard answer: atomic acquire, mandatory TTL so a dead holder can't deadlock the system forever. Straight extension of the pessimistic-lock reasoning from the caching session.
- **Hot keys** — one key drawing disproportionate traffic melts a single shard or cache node regardless of how evenly everything else spreads. Same shape as the "whale" customer from the sharding session, one layer up.
- **Fan-out on write vs fan-out on read — the celebrity problem.** Fan-out on write pushes a post into every follower's feed at publish time (fast reads, brutal writes for someone with 50M followers); fan-out on read assembles the feed at request time (cheap writes, slow reads). The real answer is **hybrid**: fan-out on write for normal accounts, fan-out on read for celebrities.
- **Geospatial indexing** — why a plain B+tree can't answer "nearest to me" (two dimensions collapsed onto one ordering), and the three practical answers: **geohash** (interleave lat/long into a sortable string so nearby points share prefixes), **quadtree** (recursively subdivide space), and **Redis GEO** as the off-the-shelf option.
- **Inverted index** — term → list of documents containing it, the structure behind every search engine, and the reason full-text search belongs in Elasticsearch rather than hand-rolled. My product-service `tsvector` + GIN index is Postgres's built-in version of exactly this.

### Key takeaways

- **The method is proven, not assumed** — 5/5 cold after a day gap. Spacing does the work; cramming doesn't.
- **A lock without a TTL is a deadlock waiting for a crash.** Atomicity and expiry are one decision.
- **Hybrid beats either pure strategy for fan-out** — the right answer is "it depends on the account," and saying so *is* the senior answer.
- **My `tsvector` column is an inverted index.** Another pattern I shipped before I could name it.

## Friday 2026-07-31 — Full design exercises: URL shortener + chat app

### What I did

- **URL shortener (end-to-end)** — requirements + scale (100M writes/month, ~100:1 read-heavy → ~4k reads/sec). Short code via base62 encoding of a counter (unique by construction, no collision checks); distributed **range allocation** (each server reserves a range up front); crash recovery principle **"burn IDs, never reuse them"** (gaps are free, reuse is corruption). Redirect path: cache (Redis) → shard by ID range → 302 vs 301 trade-off (analytics vs load). Visit counts + ID counter kept off the hot path (Redis/queue, batched).
- **Chat app / WhatsApp (end-to-end)** — clarifying questions that change the architecture (retention, receipts, group vs 1:1). Real-time via **WebSockets**. The two hard problems (found them myself): (1) a **Redis registry** for "which server is user B connected to", (2) a **pub/sub backbone** (Redis Pub/Sub / Kafka) so servers route messages to each other — you don't open sockets between servers. Offline → store in a DB inbox → deliver on reconnect → delete (WhatsApp retention). **Presence** = the WebSocket connection + a Redis key with a TTL (auto-offline when heartbeats stop); contacts pull status on-demand (push would be a fan-out storm). **Receipts** (sent/delivered/read ticks) = ACKs from B's client that advance each message's state and route back to A via the same registry+pub/sub; batch the read receipt ("read up to message X"). **Database**: NoSQL (chat is write-heavy, ~23k msg/sec), shard by `conversation_id` (sorted user IDs), pick Cassandra + Redis/queue for the inbox.

### Key takeaways

- Unique IDs: reserve ranges durably, and on crash jump forward — burn IDs, never reuse them.
- The hard part of real-time chat is routing across a fleet of stateful WebSocket servers → registry (where) + pub/sub (how).
- Receipts and presence both reuse the same message-routing machinery — good systems reuse their backbone.

- Re-drill the parked backend interview blocks (Repository, HTTP client, DB production, Kafka) on a spaced schedule.
