## Monday 2026-08-17 — Data dictionary, then the money bug (expand phase)

### What I did

- **Wrote the data dictionary before any code.** Every new column with its type, nullability, default
  and *rationale*. A Flyway migration is immutable once applied, so deciding the column list on paper
  *is* the design phase — changing your mind after V4 ships means V5 forever. Also mapped the
  **blast radius** up front: a field added to `Product` doesn't stay in product-service, it
  propagates to `ProductServiceClient` and the order snapshot. That's what makes this a three-service
  week, and it's where the estimate explodes if you don't decide it on day one.

- **Found `CLAUDE.md` was wrong about Flyway versions.** It claimed monolith V22 and product-service
  V7; the history had been squashed and the real heads were **V3, V1, V1**. Numbering a migration
  from the doc would have collided immediately. Corrected it.

- **Found the actual bug: money stored as `double`.** `price DOUBLE PRECISION` in product-service,
  `totalPrice`/`unitPrice` in order-service — six places across two services. Binary floating point
  cannot represent `0.10` exactly, so per-line rounding error accumulates. `Product.getFinalPrice()`
  was literally `price * 1.19`.

- **Did the type change as a real expand/contract** — the 07-17 rolling-deploy lesson made concrete:
  - **V2** adds `price_amount` **nullable** + backfills → an older instance running alongside the new
    one keeps inserting successfully.
  - deploy → the entity **dual-writes** both columns.
  - **V3** sets `NOT NULL`, safe only now that every writer populates it.
  - the `DROP` of the legacy column is **deliberately deferred** to a separate, later migration.
    Folding it in would defeat the whole point.

### Problems and how I resolved them

- **`CHAR(3)` stopped the app booting.** Postgres reports `CHAR` as `bpchar`; Hibernate maps a
  `String` field to `varchar`; `ddl-auto=validate` refused to build the context. Switched to
  `VARCHAR(3)` — better regardless, since `CHAR` blank-pads and buys nothing in Postgres. Editing the
  migration was legitimate *only because it had never been applied anywhere durable*.

- **Records have no overloads, so widening a DTO broke every caller** — 7 test call sites. The entity
  could keep a deprecated `double` constructor as a compatibility shim; the DTOs could not.

- **Maven's incremental compile lied.** `mvn test-compile` reported success against **stale** class
  files, so I believed the tests compiled when they didn't. Only `mvn clean test` surfaced the 7 real
  errors. Rule: always `clean` after changing a record.

### Key takeaways

- **Expand/contract is only a pattern if you actually split the deploys.** Nullable + backfill, then
  deploy, then `NOT NULL`, then — much later — `DROP`. All in one migration is a rename in costume.
- **The giveaway was already in my own test suite:** an assertion needing
  `isCloseTo(119.0, within(0.0001))`. That tolerance existed *because* the type was wrong.
  It is now `isEqualByComparingTo("119.00")`.

## Tuesday 2026-08-18 — Product enrichment + weighted full-text search

### What I did

- **Enriched the product model**: `description`, `sku` (unique, deterministically backfilled from the
  id so a re-run on a copy produces identical values), `brand`, `currency` (ISO-4217), and
  `created_at`/`updated_at` maintained by `@PrePersist`/`@PreUpdate` with DB defaults as a backstop
  for writes that bypass Hibernate.

- **Upgraded full-text search from flat to weighted.** `search_vector` indexed `name` only, so every
  match ranked equally and the new columns were invisible to search. It now carries
  name (**A**) > brand (**B**) > description (**C**) and the query orders by `ts_rank` — a term
  matching a product *name* outranks the same term buried in a *description*.

- **Moved the price filters off the deprecated column** — `search` was still filtering on `p.price`
  (the double). Now `p.price_amount`, with `BigDecimal` parameters all the way through the port.

### Problems and how I resolved them

- **Postgres has no `ALTER` for a generated column's expression**, so `search_vector` had to be
  dropped and recreated (taking its GIN index with it). Safe here *specifically* because the column
  is `GENERATED ALWAYS` — it stores no data of its own, only a derivation of columns that already
  exist. This is the one exception to the week's "no `DROP`" rule, and worth being explicit about.

- **A generated column requires every function in it to be `IMMUTABLE`.** `to_tsvector` with an
  explicit `'english'` regconfig, `setweight` and the `||` operator all qualify — the implicit
  single-argument `to_tsvector` would not.

### Key takeaways

- **Weighting is what turns full-text search into *relevance*.** Matching is the easy half; ranking
  by *where* the term matched is what users actually perceive as quality.
- **A derived column can be rebuilt freely.** Knowing which columns hold data and which hold
  derivations tells you exactly which drops are dangerous.

## Wednesday 2026-08-19 — order-service money, order metadata, keyset pagination

### What I did

- **Fixed the same money defect in order-service**, which has a compounding twist: order totals are
  **derived** (unit × quantity, then summed), so floating-point error could make an order total
  disagree with the sum of its own lines. Amounts are now `NUMERIC(12,2)`/`BigDecimal`, and totals
  sum via `BigDecimal::add` rather than `mapToDouble().sum()`.

- **Made the line total derived rather than stored.** `OrderItem` used to *accept* `totalPrice` as a
  constructor argument. It now computes `lineAmount = unitAmount × quantity` internally and
  recomputes on `setQuantity`, so the two can no longer drift apart. The old `setTotalPrice` is now
  an intentional no-op.

- **Added order metadata**: `created_at`, `updated_at`, a human-readable `order_number`
  (`ORD-2026-XXXXXXXX`, unique and backfilled — nobody reads a UUID over the phone), and
  `shipping_address` as JSONB.

- **Built keyset pagination** on `GET /api/orders/customer/{id}/history` — the feature `created_at`
  was added to make possible. `OFFSET` makes page N read and discard N×size rows, so deep pages get
  slower; the `(created_at, id) < (?, ?)` tuple comparison maps directly onto the composite index
  `(customer_id, created_at DESC, id DESC)`, so every page costs the same. Fetches `limit + 1` to
  detect a next page, which avoids a `COUNT` entirely — knowing *"is there more"* is far cheaper than
  *"how many in total"*.

### Problems and how I resolved them

- **JSONB rejected the `AttributeConverter` pattern this codebase already uses.** A converter hands
  JDBC a `String`, which binds as `varchar`, and Postgres refuses to implicitly cast
  `varchar → jsonb`. The existing `order_product_snapshot` only gets away with a converter because
  its column is `TEXT`, not `JSONB`. Fixed with `@JdbcTypeCode(SqlTypes.JSON)` — which also let me
  delete a class.

- **A malformed cursor would have been a 500.** Made it raise `IllegalArgumentException`, which
  `GlobalExceptionHandler` already maps to **400** — the 07-13 lesson about a catch-all dressing
  client errors up as server errors.

### Key takeaways

- **Derive values that can be derived.** The total disagreeing with its own lines was only possible
  because the code accepted it as an input.
- **Keyset trades a capability for consistency of cost:** no jump-to-page, no total count, but page
  5000 is as fast as page 1. The API shape has to admit that — hence a cursor, not a page number.

## Thursday 2026-08-20 — Snapshot v2: evolving a JSON column that already has rows

### What I did

- **Extended `OrderProductSnapshot` to v2** with `sku`, `brand`, `currency` and an explicit
  `version` field — the genuinely hard part of the week, because that column already holds real
  customer orders that cannot be migrated away.

- **Made v1 rows readable by design, not by luck.** Every field added in v2 is a **nullable
  reference type**, so a v1 row yields `null` rather than an exception. `price` is `BigDecimal` and
  not a primitive precisely so a missing number cannot silently become `0`. The explicit `version`
  lets readers branch on shape instead of guessing from which fields happen to be populated.

- **Extended `ProductServiceClient.ProductData` to match**, with `price` as `BigDecimal` — parsing an
  exact JSON decimal into a `double` would reintroduce the rounding error at the very boundary the
  snapshot exists to freeze.

- **Wrote the compatibility test against literal v1 JSON**, not a fixture built from the v2 record —
  the test has to prove what the *old shape* does, so it deserialises a hand-written v1 document.

### Problems and how I resolved them

- **This day was priced as the riskiest and turned out to be the safest.** `@JsonIgnoreProperties(
  ignoreUnknown = true)` was already on the v1 record, which is what makes *both* directions work:
  a v1 reader tolerates v2 JSON, and a v2 reader tolerates v1 JSON. No migration of the stored
  documents was required at all. Worth noting that the safety came from a decision made months
  earlier, not from anything I did this week.

### Key takeaways

- **A JSON column is a schema too.** It evolves, it needs versioning, and old rows must keep
  parsing — nullable reference types, never primitives, and an explicit version tag.
- **Forward-compatibility annotations pay off long after you write them.** `ignoreUnknown` cost
  nothing on day one and removed an entire migration on day 90.

## Friday 2026-08-21 — Monolith users, frontend surface, and end-to-end verification

### What I did

- **Enriched the monolith's users**: audit timestamps, `phone`, and `default_address` as JSONB. The
  default address is a **copy source**, not a shared reference — checkout copies it into the order's
  own `shipping_address` so a customer moving house cannot rewrite where past orders were shipped.
  Same reasoning as the product snapshot.

- **Wired the frontend**: brand, SKU, description and currency-aware pricing on the product card and
  detail views (`CurrencyPipe` replacing a hardcoded `$` — the API says EUR, so the UI now says EUR);
  order number, date, per-line subtotal, snapshot brand and shipping city on the order list; and
  **"Load more"** replacing Previous/Next, because a cursor is a *position*, not an offset, and the
  UI shouldn't pretend otherwise.

- **Rebuilt and restarted the local stack** to verify against databases holding five-week-old real
  data — not fresh fixtures.

### Problems and how I resolved them

- **The frontend had no customer id**, and the keyset endpoint is customer-scoped. `AuthResponse`
  carries only `token`/`email`/`role`. But `JwtService` sets `subject = user.getId()`, so the id was
  in the token all along — decoded the `sub` claim client-side. Documented explicitly that this only
  *decodes*, never verifies, and must never be trusted for authorisation; the server validates the
  token on every request, and this is used purely to build a URL.

- **Discovered "My Orders" never showed my orders.** It called `GET /api/orders` (`getAll`), which
  returns **every order in the system**. Moving to the customer-scoped history endpoint fixed a real
  pre-existing bug as a side effect.

### Verification

- **8 migrations applied cleanly** to live data — product-service → V5, order-service → V4,
  monolith → V4.
- **The money fix on real rows:** `11.899999999999999 → 11.90`; `42.50 × 1.19 → 50.58` (half-up from
  50.575); `129.99 × 3 → 389.97` exactly. JSON now serialises `10.00`, not `10.0` — `BigDecimal`
  preserves scale over the wire.
- **Backward compatibility proven on genuine v1 rows:** orders written five weeks ago return
  `{"version": null, "sku": null, "brand": null, "currency": null, "name": "G2", "price": 10.0}` —
  nulls where v1 had nothing, `name`/`price` intact, no error.
- **Weighted search** ranks *Ergonomic Keyboard* (name match) above *Standard Mouse* (description
  match).
- **Keyset walk:** page 1 → cursor decodes to `2026-08-21T12:15:58Z|c62ff50e-…` → page 2 completes
  with `hasMore: false`. A malformed cursor returns **400, not 500**.
- **75 tests green** — product 40, order 21, monolith 14, up from 54.
- Shipped as five commits on `feat/domain-enrichment`: 63 files, +1611/−133.

### Key takeaways

- **Store money as exact decimal, always.** Six places, two services, and the live stack was
  returning `11.899999999999999` to real users.
- **Verify against real data, not fresh fixtures.** Every test passed on a clean Testcontainers
  database. The interesting confirmations — backfilled SKUs, v1 snapshots, the floating-point
  artefact itself — only appeared against five-week-old rows.
- **Trust the build, not the tool's summary.** Incremental compilation reported green against stale
  classes and I repeated that claim before checking.
- **Additive changes let the frontend lag safely.** Every API change this week was additive, so the
  Angular app kept working untouched for four days and only needed updating when I chose to surface
  the new fields.
