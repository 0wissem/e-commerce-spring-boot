- **Opened with cold retrieval on last Monday's material** rather than re-reading it — the four metrics and their trade-offs, the honest version of CAP (partitions aren't optional, so the real choice is C *or* A), and the one that matters most: *my own system already made that choice.* The monolith and product-service hold separate databases, so a network split between them means the order-creation path can't fetch a product snapshot. I chose availability and eventual consistency the day I picked the snapshot over the join — I'd just never named it.

- **Built the scaling ladder as an ordered model**, because the order *is* the answer: (1) **vertical scaling** — bigger box, correct far longer than engineers admit, especially once the working set fits in RAM; (2) **read replicas** — scales reads only, since every replica still applies every write, and you buy it with **replication lag**; (3) **functional partitioning** — split by domain; (4) **horizontal sharding** — one table across N machines, the expensive and effectively irreversible rung. Jumping straight to "shard it" is the marked-down answer.

- **Realised rung 3 is something I have already shipped.** Splitting the monolith into monolith/product-service/order-service with one Postgres each *is* functional partitioning — "vertical sharding" in system-design vocabulary. And I've already paid its price: the moment products left the monolith, `orders JOIN products` stopped existing and became an HTTP call plus a JSONB snapshot. That's a claim I can now make concretely — I've scaled a data layer by domain and lost my joins doing it.

- **Worked the shard-key decision on `orders`**, the table that actually grows without bound (products are ~10k and capped). Three properties in tension: **even distribution**, **query locality**, and **stability** of the key.
  - `order_id` (hash) → perfect spread, but "show me my order history" doesn't know which shard holds the rows, so it fans out to all N and waits on the slowest. The dominant query becomes the slowest one.
  - `created_at` (range) → trivial to archive and rebalance, but **every insert lands on today's shard**. All writes on one machine — the planted wrong answer.
  - `customer_id` (hash) → one customer's history lives on one shard, so the dominant read is single-shard. Distribution is *nearly* even, with hot-shard risk from an outlier enterprise customer.
  - **Call: `customer_id`** — locality over perfect distribution, because the dominant access pattern is per-customer. The reasoning is the answer, not the key.

- **Listed what breaks after sharding:** cross-shard joins (reassemble in app code or denormalize), cross-shard transactions (no more single-DB ACID → sagas or 2PC), rebalancing (naive `mod N` remaps nearly every row → **consistent hashing** moves only ~1/N), and hot shards.

### Key takeaways

- **Sharding is the last rung, not the first.** Vertical → replicas → functional partitioning → horizontal sharding. Naming the order matters more than knowing the mechanics of the last rung.
- **Read replicas scale reads, never writes.** Every replica applies every write; the write ceiling is unchanged. What you're really buying is throughput in exchange for staleness.
- **The shard key is the whole decision, and it's irreversible.** Even distribution, query locality, and stability pull against each other — you pick which one to sacrifice, and you justify it from the dominant access pattern.
- **I've already lived rung 3.** The Strangler Fig extraction was functional partitioning, and the JSONB snapshot was the bill for it. The CAP choice was made in my code before I had the vocabulary for it.
- **Vocabulary converts experience into credibility.** Nothing about my system changed today; what changed is that I can name what I built — vertical sharding, availability over consistency, locality over distribution.
