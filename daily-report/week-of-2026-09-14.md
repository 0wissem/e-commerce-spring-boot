## Tuesday 2026-09-15 — Waking up a three-month-old cluster

### What I did

- **Freed the memory first.** minikube wants 6 CPU / 6.5 GB and Docker Desktop caps at 7.8 GB here, so
  the compose stack had to come down before the cluster could come up. The two cannot coexist on this
  machine — worth knowing before blaming anything else for being slow.
- **Started the June cluster** and found it full of stale workloads: pods in `Error`, ArgoCD and the
  Kubernetes dashboard still running and eating RAM. Scaled ArgoCD and the dashboard to zero; kept the
  `monitoring` namespace, because Prometheus and Grafana are exactly what I need for consumer lag.
- **Applied all the manifests** (namespace, config, Postgres, apps, HPA, Kafka, notification-service).
  Everything came up: Kafka with its PVC, Mailpit, a fourth Postgres for notifications.

### Problems and how I resolved them

- **`kubectl apply` reported "configured" but nothing actually changed in the running pods.** The image
  tag `:latest` is identical, so the Deployment spec is unchanged, so no rollout happens — the pods
  kept running whatever they were already running. `kubectl rollout restart` is what re-pulls.

### Key takeaways

- `apply` is declarative about the *spec*, not about the *bytes*. Same tag = same spec = no restart.

## Wednesday 2026-09-16 — Green pods, missing topic

### What I did

- **Verified the event backbone instead of trusting the dashboard.** Every pod was Running and every
  probe green — but `kafka-topics --list` showed only `stock.low.DLT`. The `stock.low` topic, which
  product-service declares as a `NewTopic` bean, did not exist.
- **Followed the silence.** notification-service was warning in a loop about an unknown topic, and
  product-service's log contained **not one Kafka line** — no admin client, no producer config. Env
  vars were right (`KAFKA_BOOTSTRAP_SERVERS=kafka:9092`), the config map was right.
- **Wrote down what made it silent**, because that is the actual defect:
  - `spring.kafka.admin.fail-fast=false` lets a service with a broken admin client start up clean;
  - a missing topic is a *warning* on the consumer side, not a failure.

### Key takeaways

- "All pods Running" says the processes are alive, not that they are doing their job. The only honest
  check is the one that asks the dependency: does the topic exist, is the group consuming, is lag
  falling.
- Fail-fast settings are a choice about *where* you want to find out. I chose startup-tolerant and
  paid for it with a silent cluster.

## Thursday 2026-09-17 — The image that would not update

### What I did

- **Compared what I deployed with what was running**, and they were different: the pod's imageID was
  a June build, while the image I had built locally had a completely different digest under the same
  `:latest` tag. The cluster had been running pre-Kafka code all along.
- **Tried the documented route** — `minikube image rm` then `minikube image load` — and the pods still
  came up on the old image.
- **Checked the runtime** rather than guessing: the node reports docker, so the daemon I was inspecting
  really is the kubelet's image store. The mismatch was real, not a tooling illusion.

### Problems and how I resolved them

- **My own verification lied.** The loop I wrote to compare local and in-cluster image IDs printed
  "OK" for all five services while two of them did not match — it was comparing strings that could
  never match cleanly. It ended the investigation early, twice.
  A check that cannot fail is worse than no check at all: it manufactures confidence.

### Key takeaways

- `:latest` plus `imagePullPolicy: IfNotPresent` means the manifest cannot express "this exact build".
  Immutable tags (the git sha) are the real fix, and that is now a concrete reason, not a style
  preference.
- Verify a verification. If a check has never failed, I don't yet know that it can.

## Friday 2026-09-18 — zsh ate the tag

### What I did

- **Found the root cause of the stale image, and it was my shell.** The build loop used
  `-t spring-boot-0-$s:latest`. In **zsh**, `$s:l` is the *lowercase* parameter modifier — so the tag
  became `spring-boot-0-product-serviceatest`, and the real `:latest` tag kept pointing at June's
  build. Quoting it (`"spring-boot-0-${s}:latest"`) fixes it.
- **Stopped shipping images over the wire.** Now I build straight into the cluster's own daemon with
  `eval $(minikube docker-env)`, so there is no copy step left to get wrong, then
  `kubectl rollout restart`.
- **Re-verified properly**: `stock.low` created with 3 partitions, product-service logging its admin
  and producer config, notification-service assigned to all three partitions.
- **Smoke-tested the whole chain through the gateway in the cluster:** created a customer and a product
  with stock 7, ordered 3 → stock 4 → one email in the Mailpit inbox.

### Key takeaways

- Shell quoting is not cosmetic. `$var:latest` in zsh is a silent, successful, wrong build.
- When two systems must hold the same artefact, the best fix is to remove the copy, not to make the
  copy more careful.
- End of week: the feature runs on Kubernetes. Nothing committed — nothing here was a code change.
