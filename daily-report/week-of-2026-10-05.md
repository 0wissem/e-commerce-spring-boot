# Weekly Report — Week of Monday 2026-10-05

> Engineering log. Fixed a flaky test honestly, then re-ran the same outage experiment on the cluster
> to get before/after numbers. The fix holds: the main topic drains in ~40 s instead of ~190 s.

## Monday 2026-10-05 — A flaky test is a bug in the test

### What I did

- **Ran the full suite and the new regression test failed — but only in the full suite**, not when run
  alone. The temptation was to widen the 3-second budget, which would have deleted the thing the test
  measures.
- **Found the real cause instead.** The test asserts on a stopwatch, and four listener containers
  (main topic, two retry topics, DLT) join the consumer group at startup; the rebalance had not
  finished when the clock started. The test was failing on startup timing, not on behaviour.
- **Removed the timing dependency**: the test now waits until the container actually owns its partition,
  then starts measuring. Also created its topic in a static block rather than on first send, so the
  consumer is not waiting on a metadata refresh for a topic that did not exist at startup.
- **Ran the whole suite twice: 23 tests green both times.**

### Key takeaways

- The fix for a timing-flaky test is to remove the timing, not to widen the window. Widening it is how
  a real regression gets through later.
- Two green runs, not one. A single pass of a concurrency test is an anecdote.

## Tuesday 2026-10-06 — Before and after, same experiment

### What I did

- **Rebuilt the image inside the cluster's daemon and rolled out notification-service.** The retry
  topics appeared on their own: `stock.low-retry-1000`, `stock.low-retry-2000`.
- **Repeated Thursday's outage experiment exactly** — Mailpit scaled to zero, 30 crossings:

  | | main-topic drain | consumption rate | where failures waited |
  |---|---|---|---|
  | blocking backoff (before) | ~190 s | 0.27 events/s | on the consumer thread |
  | retry topics (after) | **~40 s** | unaffected by failures | on the retry topics |

  The lag moved from the main topic to the retry topics, which is precisely the intent: healthy events
  are not behind broken ones any more.
- **Checked the recovery path too:** brought Mailpit back and placed a fresh order — the alert was
  emailed in **1 second**, while the exhausted records from the outage sat in `stock.low.DLT` **with
  the failure reason attached**.
- **Confirmed the arithmetic end to end:** 60 dead letters across the two experiments, matching the
  sum of the per-pod counters (39 + 21).

### Key takeaways

- The same experiment before and after is worth more than any amount of explaining. Two numbers,
  one decision.
- "Where does the lag live?" is a better question than "how much lag is there". Moving it to a retry
  topic is the whole fix.

### Key takeaways

- **Three weeks, one commit, and the commit is small.** The work was reproducing a failure under load
  and reading metrics; the code change is an annotation, a config class and a test. That ratio is
  normal for an operational bug, and worth saying plainly rather than apologising for.
- The order that actually worked: make it reproducible → measure → state a hypothesis → let the
  measurement kill it → fix the thing the numbers point at → encode it as a test.
- The two defects that cost the most were both about **silence**: a cluster running old code with every
  probe green, and a dead letter with no reason. Neither was a crash. Observability is not a dashboard,
  it is making the quiet failures loud.
