# Weekly Report — Week of Monday 2026-09-28

> Engineering log. Replaced the blocking retries with retry topics. The switch broke three things that
> had been working silently, and each one was caught by a test rather than by luck.

---

## Monday 2026-09-28 — Non-blocking retries, and an API that moved

### What I did

- **Switched the listener to `@RetryableTopic`.** A failure is now forwarded to `stock.low-retry-1000`
  / `-retry-2000` and the main topic keeps flowing; exhausted records land in `stock.low.DLT`.
  Permanent failures (bad JSON, an event with no product id) are listed in `exclude`, so they skip the
  retry topics entirely.
- **Replaced the DLT listener with `@DltHandler`.** It is part of the same retry configuration, so
  Spring routes exhausted records to it and never applies another error-handling hop. The old plain
  listener on the DLT topic was a latent loop: if it ever threw, the global error handler would
  republish the failure to the same dead-letter topic, forever.

### Problems and how I resolved them

- **The annotation I expected does not exist in Spring Kafka 4.** `@RetryableTopic(backoff = @Backoff(…))`
  from spring-retry is gone; version 4 has its own `@BackOff` annotation, and only the `*String`
  attributes accept a property placeholder. Found it by listing the annotation's methods in the jar
  rather than by trusting an older blog post.

### Key takeaways

- Blocking vs non-blocking retries is a *topology* decision, not a tuning knob: it decides whether a
  slow dependency costs you one record or the whole partition.
- When a major version moves an API, read the artefact you actually depend on.

## Tuesday 2026-09-29 — One fewer attempt than I thought

### What I did

- **Ran the suite and watched three tests go red**, which is exactly what the suite is for.
- **Tracked down the first failure: the attempt semantics changed under me.** `DefaultErrorHandler`'s
  `maxRetries` counts retries *after* the first delivery; `@RetryableTopic`'s `attempts` counts
  **total** attempts. Same number in the config, one fewer try in practice — so the test that fails
  twice and succeeds on the third attempt never got its third attempt.
- **Renamed the property to `app.kafka.retry.attempts`** so the two meanings can never be confused
  again, and documented it where it is read.

### Key takeaways

- When migrating between two implementations of "the same" concept, the off-by-one is in the
  vocabulary, not in the code. Renaming the property is the fix; a comment would have rotted.
- A test that asserted "sent on the third attempt" is what caught it. A test asserting only "sent
  eventually" would have passed and hidden a 33% reduction in resilience.

## Wednesday 2026-09-30 — A dead letter with no reason

### What I did

- **Chased the second failure: `reason=[null: null]` in the dead-letter log.** The retry-topic
  recoverer forwards only `kafka_original-topic`; it does not write Spring's `kafka_dlt-exception-*`
  headers that the blocking error handler used to add. The parking lot still caught the records, but
  an operator opening one could no longer see *why* it died.
- **Tried the framework knob first** (`includeHeader(...)` on the recoverer) and it did not take
  effect — the retry factory replaces the header set.
- **Stopped fighting the version and owned the contract.** `RetryTopicConfig` now stamps
  `x-failure-class` and `x-failure-message` from the **root** cause, because what arrives is a
  `ListenerExecutionFailedException` wrapper and "listener failed" tells nobody anything. The
  `@DltHandler` logs those, and the tests assert on them.

### Key takeaways

- The reason *is* the feature of a dead-letter topic. A DLT you cannot triage is a bin.
- When framework-provided metadata is incidental to your operations, write your own: two headers you
  control will survive the next upgrade.

## Thursday 2026-10-01 — Taking over a configuration means taking over all of it

### What I did

- **Hit a context that would not start:** *"Either a RetryTopicSchedulerWrapper or TaskScheduler bean
  is required."* Subclassing `RetryTopicConfigurationSupport` to customise the headers makes Boot's
  retry-topic auto-configuration back off — and the scheduler it had been providing disappears with it.
- **Declared the scheduler myself**, with a named thread prefix. It is also the thing that makes the
  retries non-blocking: a record on a retry topic waits *there*, held by this scheduler, instead of on
  a consumer thread.
- **Re-ran the consumer suite: all 8 green**, and the dead-letter log now reads
  `reason=[org.springframework.mail.MailSendException: SMTP down …]`.

### Key takeaways

- Boot's auto-configuration is all-or-nothing per area: the moment you extend the support class, every
  bean it used to supply becomes yours. The error message was precise — read it, don't pattern-match it.

## Friday 2026-10-02 — The regression test that encodes three weeks

### What I did

- **Wrote `HeadOfLineBlockingTest`**, which states the bug as an assertion: a failing event, then a
  healthy event behind it **on the same partition** (same key), with the retry delay set to 4 seconds.
  The healthy one must be processed in under 3. It runs with its own topics and its own consumer group
  so it cannot steal partitions from the other test context.
- **Proved it catches the bug**: temporarily put the blocking retries back, and it failed on the clock —
  the healthy event was still unprocessed after 3 seconds. Restored the fix; it passes in 4 seconds
  total.

### Key takeaways

- The right regression test for a performance bug asserts on **time**, not on a side effect. "Both
  events were eventually processed" passes in both worlds and protects nothing.
- Three weeks of investigation compress into one test that runs in four seconds. That is the artefact
  worth leaving behind, more than the fix itself.
