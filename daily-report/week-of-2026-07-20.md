## Monday 2026-07-20 — System Design fundamentals: metrics, trade-offs, CAP theorem

### What I did

- **Shifted from interview-drill mode to System Design / Architecture.** The goal: learn to think like a software architect, not just pass an interview round. Started with foundational concepts that apply to every system.

- **Mastered the four core metrics and their trade-offs.** Every system optimizes for some combination of: (1) **latency** (how fast), (2) **throughput** (how many concurrent), (3) **availability** (always up), (4) **consistency** (correct/fresh data). The constraint: you pick two, sacrifice one. Worked through four real scenarios to internalize this:
  - **Product search** (millions/day, prices change hourly) → prioritize throughput, sacrifice consistency (10s stale is OK)
  - **Payment system** (must be accurate) → prioritize consistency, sacrifice throughput (fewer concurrent payments, but each is correct)
  - **Notifications** (millions of users, must be always up) → prioritize availability, sacrifice consistency (notifications might dupe/reorder)
  - **Analytics dashboard** (scan millions, updates daily) → prioritize throughput, sacrifice both latency (30s queries acceptable) and consistency (1-day stale expected)

- **Internalized the pattern:** constraints are natural (what your system needs to handle). Name the constraint → identify which metric matters → sacrifice the least-important one. This is the architect's core skill — not how to implement, but what to trade off.

- **Introduced CAP theorem:** in a distributed system (multiple servers), you have at most 2 of 3 — **Consistency, Availability, Partition tolerance**. Since network failures always happen (partition is inevitable), you really choose between consistency and availability. During a network split: stop accepting writes (consistency) or keep running with diverging data (availability). You can't have both.

### Problems and how I resolved them

- **Confused by "pick two, sacrifice one"** initially — treated it as abstract rules rather than concrete trade-offs tied to real constraints. Resolved by working through scenarios and asking "what does this system actually need?" — the constraint reveals what to sacrifice.

### What I'm planning

- Continue System Design fundamentals: **database partitioning/sharding** (how to scale when one server can't hold the data), **caching strategies** (cache-aside, write-through, etc.), **message queues** (async processing, decoupling), **load balancing**, and **API design**.
- Then move from theory to practice: design real systems from scratch (Twitter clone, ride-sharing, etc.) to apply the metrics + trade-offs.
- Revisit the interview-drill blocks (Repository, HTTP client, DB production, Kafka) on a spaced schedule to keep them retained.

### Key takeaways

- **Every system has constraints; constraints dictate trade-offs.** Don't optimize for all four metrics — identify what the system actually needs and sacrifice wisely.
- **Consistency and availability are opposites under network failures.** You can't have both when servers can't talk to each other. Pick one.
- **The architect's job is deciding what to trade off, not how to implement.** Engineers build; architects decide what to sacrifice.
- **Patterns repeat across systems.** Product search, notifications, analytics, payments — each teaches the same principle in a different context.

## Tuesday 2026-07-21 — System Design: database sharding end to end

### What I did

- **Worked through sharding (horizontal database partitioning) from scratch**, reasoning out each problem rather than memorising rules:
  - **Hash routing** — `hash(shard_key) % N` maps each key deterministically to one of N shards, so the same customer always lands on the same shard.
  - **Hot shards / the "whale"** — hashing spreads customers evenly but not load; one B2B reseller placing 40% of orders melts a single shard. Fix: isolate the whale onto its own shard to protect its co-tenants (the ~100k innocent customers sharing that shard), and vertically scale that dedicated box since it carries disproportionate load. Isolation alone just moves the fire — you need both, and only when the load actually hurts neighbours (measure first, don't pre-isolate).
  - **Shard key choice** — whatever you shard by is fast; every other access pattern gets expensive (shard by `order_id` and "list a customer's orders" becomes a scatter-gather across all shards). Rule: pick the key matching the most common query, handle the rare outlier separately.
  - **Resharding pain** — naive `% N` means adding a shard (`% 10` → `% 11`) reshuffles almost all data. The fix is consistent hashing / ranges: because a hash has a fixed maximum (e.g. 0–4B), you assign each shard a range of that fixed space; adding a shard splits one range in two, moving only a small slice while every other shard stays put.
  - **Shard splitting** — reasoned my way to this production technique independently (keep the old mapping, split only the overloaded bucket). Good for one-off growth; consistent hashing is for continuous, repeated growth without special-case code.

### Key takeaways

- **Sharding trades scale for consistency** — cross-shard transactions can't be atomic, so you avoid cross-shard writes or accept eventual consistency.
- **A fixed hash ceiling is what makes range-based sharding possible** — no `% N`, so adding a shard subdivides the space instead of reshuffling it.
- **The shard key is the indivisible unit** — everything sharing that key lives together on one shard, always.

## Wednesday 2026-07-22 — System Design: caching strategies, deeply

### What I did

- **Named the pattern my own project already uses: cache-aside** (`@Cacheable` on `getById` — check cache, miss → DB → store; `@CacheEvict` on update/delete). Confirmed against the real code: only single-product-by-ID reads are cached; pagination/lists are one SQL query and correctly not hand-cached.
- **Write patterns compared:** evict-on-write (project's choice, simple), write-through (DB + cache together, always fresh, slower writes), write-behind (cache now, DB async — fast but data-loss risk). Picked the right one per use case (never write-behind for a bank balance).
- **The stale-read race** — a slow reader can repopulate the cache with old data after a writer's evict, leaving cache and DB out of sync until TTL. This is why TTL is the safety net, and why "cache invalidation is one of the two hard problems."
- **Pagination + caching** — reasoned to the normalized approach (cache page → list of IDs, cache products individually), then learned the real big-company practice: individual items in Redis (by ID), lists/search/pagination in Elasticsearch, hot public pages at the CDN — used together, each for its strength.
- **Keyset pagination** — `WHERE id > last_seen LIMIT 20` instead of `LIMIT 20 OFFSET 100000`; uses the index to jump instead of scanning+discarding rows, so every page is equally fast. Trade-off: next/prev only, no random page jumps — perfect for infinite scroll.
- **Cache stampede / thundering herd** — when a hot key's TTL expires, thousands of simultaneous misses hit the DB at once. Fixes: a lock (one request reloads, the rest wait — I derived this from the DB pessimistic-lock idea), jitter on TTLs, background refresh, serve-stale. Learned `refreshAfterWrite` (serve old + reload async, no empty gap) vs `expireAfterWrite` (delete + gap) vs `maximumSize` (the actual memory cap, LRU eviction).
- **Eviction policies:** LRU (least recently used — Caffeine default), LFU, FIFO. Eviction is by last-access time, not insertion order.
- **Distributed cache** — Caffeine is per-instance, so N replicas hold N inconsistent caches; an evict on instance A leaves B and C stale. Fixes: broadcast eviction (messaging/pub-sub) or a shared Redis cache (one source of truth, at the cost of a network hop and new infrastructure). Often both: Caffeine (L1 local) + Redis (L2 shared).

### Key takeaways

- **Memory is bounded by `maximumSize`, freshness by expire/refresh** — different knobs, different jobs.
- **Don't hand-cache lists** — push them to a search engine (Elasticsearch); cache individual entities by key.
- **A cache is load-bearing, not just speed** — its failure modes must be designed for.

## Thursday 2026-07-23 — System Design: resilience patterns (half-day, afternoon off)

### What I did

- **Circuit breaker (Resilience4j)** — lives as a library in the caller (e.g. order-service), not a separate server. States: CLOSED (normal) → OPEN (too many failures → stop calling, fail fast) → HALF-OPEN (test one request → recovered? close : re-open). Key mental model: the breaker runs in the healthy caller and watches the failing callee — "product-service is down" never means order-service's code can't run. Protects the caller from draining its own thread/connection pool on a dead dependency (ties directly to the connection-pool-exhaustion bug I found earlier).
- **Fallback / graceful degradation** — when the breaker is OPEN, return something useful (stale cached data, a "received, confirming shortly" response) instead of a hard error.
- **The optimistic-promise trap** — a fake "accepted!" is a lie if the system can't complete it. The honest pattern: persist the intent (save as PENDING in a DB you own), respond truthfully, complete asynchronously when the dependency recovers, notify the real outcome (confirm/refund). This is the Outbox pattern again — eventual consistency, with a Saga to compensate on failure.
- **Rate limiting** — protect the API from abuse at the gateway (single entry). Algorithms: token bucket (allows bursts, most common), fixed/sliding window, leaky bucket. Counter in Redis so it's shared across gateway instances. Blocked requests → 429 Too Many Requests.
- **Load balancing** — a real component (Nginx/HAProxy/AWS ALB) in front of N servers. Strategies: round robin (default), least connections (uneven request cost), geographic (latency), weighted (unequal servers), IP hash (stickiness). Round robin is per-request, not per-user — which only works because servers are stateless (state in DB/Redis/JWT, not server memory). Health checks auto-remove dead servers. Internal service-to-service calls are load-balanced too (e.g. Kubernetes Service).
- **JWT vs shared session** — pure JWT is stateless (any server verifies the token, no store needed) but can't be revoked. To revoke (logout/ban), add a Redis blocklist — which re-introduces a little state. Many systems use short-lived JWTs to avoid the blocklist.

### Key takeaways

- **Resilience is a stack:** timeout → retry → circuit breaker → fallback. Each handles a different failure.
- **The circuit breaker lives in the caller, watching the callee** — it protects the healthy service from the dead one.
- **Statelessness is the enabler** — it's what makes load balancing, horizontal scaling, and failover "just work" (same lesson as stateless Spring beans).

## Friday 2026-07-24 — System Design: async processing, idempotency & database indexing

### What I did

- **Async processing / message queues** — do only what the user needs now synchronously (save the user), push slow work (email, report) to a queue (producer → queue → consumer/worker), respond instantly. Also more resilient: a job survives a downstream outage and retries.
- **Idempotency & delivery semantics** — a crashed worker can't know whether the email actually sent before it died (the same "silence" ambiguity as an HTTP timeout). So you choose at-least-once (retry, risk duplicates → make consumers idempotent via a dedupe key) or at-most-once (skip, risk misses). Exactly-once is an illusion built from at-least-once + idempotency.
- **Why an index speeds up reads but slows writes** — an index is a second, sorted structure kept beside the table. Reads become a few hops instead of a full scan; every INSERT/UPDATE/DELETE must also update the index, synchronously (inside the transaction, before commit) — otherwise a row just written wouldn't be findable via the index. More indexes → faster reads, slower writes → index only the columns you search/filter/join on.
- **How the index is structured — the B+tree** — walked through a 20-value example: a root of "signposts" routing the search, sorted leaves holding values + row pointers, leaves linked left→right for range scans. A lookup (`WHERE id = 55`) is ~2 hops instead of 20 comparisons; the tree grows wider not taller, so a billion rows is still ~5 hops (logarithmic depth).
- **Node splits (why writes cost)** — inserting into a full leaf overflows → splits in half → pushes the middle key up as a new signpost, keeping the tree balanced. If the parent/root overflows it cascades upward, and a root split is the only way the tree gains a level — which is why it stays shallow. Averaged out: inserts cheap, occasionally a split, rarely a cascade — never free.
- **What indexes make fast:** exact match (`= 55`) and range scans (`BETWEEN 30 AND 60` — find the start, walk linked leaves) — the latter is exactly why keyset pagination (`WHERE id > 40`) is fast.

### Key takeaways

- **An index is a sorted tree kept in sync on every write** — fast reads paid for with write overhead and storage.
- **B+trees stay shallow by design** — grow sideways (leaf splits), only deepen when the root splits, so lookups stay ~log(n).
- **You cannot know an operation's outcome across a process/network boundary** — pick which risk (duplicate vs miss) you tolerate, and design idempotency where it matters.
