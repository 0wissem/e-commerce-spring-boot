## Tuesday 2026-09-08 — A broker of my own, and the contract before the code

### What I did

- **Picked the parked Kafka exercise back up.** The monolith once had a low-stock alert; it was
  removed in Phase 5 and never rebuilt. The plan for the week:
  `product-service --stock.low--> notification-service`. Kafka earns its place here because
  product-service should not know *who* cares that stock ran low — today an email, tomorrow a
  restock bot. A consumer becomes a new deployment, not a change to the producer.

- **Added Kafka to docker compose in KRaft mode** — the broker is its own controller, so no
  ZooKeeper. The part that always bites: **two listeners**. A broker doesn't just accept
  connections, it hands clients an address to come back on. Containers need `kafka:29092`,
  tools on my Mac need `localhost:9092`. One listener means whoever isn't on that network fails
  with a confusing timeout.

- **Disabled topic auto-creation deliberately.** A typo in a topic name should fail loudly, not
  quietly create a second topic with default settings that nobody ever reads. Topics are declared
  in code by their owner instead.

- **Added Kafka UI (:8085) and Mailpit (:8025)** — the first to see topics, partitions, groups and
  lag; the second is a fake SMTP server that catches every email and shows it in a web inbox, so
  the whole feature runs locally with nothing leaving my machine.

- **Spent the session on the command line before writing any Java**, which is the part I actually
  needed. Produced keyed messages, read them back with partition and offset printed, and watched:
  - the same key always lands on the same partition (`p-1` → partition 1, every time);
  - reading does not consume — a **new** consumer group re-reads the whole topic from offset 0;
  - lag is just arithmetic: log-end offset minus the group's committed offset.

- **Wrote the event contract first**, as a record: `eventId`, `schemaVersion`, `productId`,
  `productName`, `stockQuantity`, `threshold`, `occurredAt`. Every field earns its place —
  `eventId` is the consumer's idempotency key, `schemaVersion` is how the contract evolves,
  `productId` doubles as the message key. Deliberately **no shared library** between the two
  services: each owns its copy of the shape. A shared jar would couple both deploys to one
  release, which is the distributed monolith.

### Key takeaways

- **The advertised listener is the whole trick.** The broker tells the client where to reconnect;
  get it wrong and it works from one network and hangs from the other.
- **A topic is a log, not a queue.** Reading doesn't remove anything, and a new group starts from
  the beginning. That single fact explains consumer groups, replay, and why renaming a group is
  dangerous.
- **The contract is the interface, not the Java class.** What crosses the wire is JSON field names.

## Wednesday 2026-09-09 — Publishing after commit (and proving why)

### What I did

- **Replaced the no-op publisher with a real one.** The port `IStockEventPublisher` already existed
  in the domain with a do-nothing implementation behind it — a placeholder from an earlier phase.
  The domain and the service did not change at all; only the adapter behind the port did. That is
  the payoff of ports and adapters, and it was a one-file swap.

- **Made the rule a domain object, `LowStockPolicy`** — pure Java, no framework. The rule is a
  **crossing**, not a level: `before > threshold && after <= threshold`. "Alert whenever stock is
  at or below 5" would fire on every sale of an item that is already low: 5 → 4 → 3 → 2 sends four
  emails for one situation. Restocking above the threshold re-arms it.

- **Published AFTER the transaction commits**, via `@TransactionalEventListener(AFTER_COMMIT)`.
  This is the decision of the week. The service raises the event inside the transaction, but
  nothing reaches Kafka until that transaction commits. It matters here specifically because of
  the optimistic locking I built two weeks ago: the version conflict only surfaces **at flush**,
  after my publish line has already run. Sending inline would alert for decrements that are about
  to be rolled back and retried.

- **Keyed every message by productId**, so all events for one product land on one partition and
  stay in order. Keyless messages are spread round-robin and can be processed out of order.

- **Made the relay swallow its own failures.** The stock change is already committed when it runs.
  Failing the HTTP call at that point would tell order-service "the decrement failed" when it
  succeeded — and order-service would compensate a reservation that really happened. It logs
  instead. I also capped `max.block.ms` at 3s: `send()` blocks while fetching metadata, on the
  request thread, so a dead broker must not hold an HTTP request for the default 60 seconds.

- **Proved the after-commit decision instead of asserting it.** I temporarily swapped the
  transactional listener for a plain one and re-ran the suite. Two tests went red exactly as
  predicted: a **phantom alert after a rolled-back transaction**, and **2 alerts instead of 1**
  when 10 threads raced through the threshold — every optimistic-lock loser had computed the same
  crossing before losing at commit.

### Problems and how I resolved them

- **Nothing was auto-configured at first.** The pom had bare `spring-kafka` instead of
  `spring-boot-starter-kafka`, so there was no `KafkaTemplate` and no admin client. This is the
  **same root cause as the Flyway incident**: Boot 4 split auto-configuration into per-technology
  modules, and the bare library compiles perfectly while configuring nothing. I had previously
  written this off as "Boot 4 needs `@EnableKafka`" — that explanation was wrong, and now I know
  why.

- **Turned off the type header.** Spring's JSON serializer adds a `__TypeId__` header carrying the
  producer's Java class name. A consumer that trusts it is coupled to my package layout: rename a
  package and the other service breaks. The consumer should decide what type to read into.

### Key takeaways

- **Publish after commit, always.** A transaction that rolled back must not have told anyone
  anything — and with optimistic locking, "did it commit?" is not answered until flush.
- **A test that passes before and after the fix proves nothing.** Breaking the fix on purpose is
  the only way to know the test is real.
- **Bare library vs starter is a recurring Boot 4 trap**, and I have now hit it twice.

## Thursday 2026-09-10 — notification-service: a consumer that can be delivered the same event twice

### What I did

- **Built notification-service**, the fifth deployable service, with the same hexagonal layout as
  the others (domain / application / infrastructure / api) and its own PostgreSQL database. The
  Kafka listener lives in `api/` beside the REST controller, because it plays the same role: an
  inbound adapter translating an external trigger into a call on the application service.

- **Made the consumer idempotent, which is the whole point.** Kafka gives at-least-once delivery,
  so duplicates are normal, not exotic — a producer retry, a rebalance, or a consumer that crashed
  after sending the email but before committing its offset. Three parts:
  1. the `event_id` column has a **UNIQUE constraint** — the "have I seen this?" lookup is only a
     fast path, the constraint is what actually closes the check-then-insert race;
  2. the row is written **PENDING before** the email and flipped to **SENT after**;
  3. a redelivery of a SENT event does nothing.

- **Chose the failure direction on purpose.** Writing PENDING first means a crash mid-flight
  resends the email rather than losing it. Exactly-once is not available — SMTP cannot join a
  database transaction — so the honest choice is "maybe twice" over "maybe never", and for an
  alert that is right.

- **Kept the email out of the transaction.** No `@Transactional` around the handler; each
  repository call is its own short transaction and the SMTP round trip happens between them. This
  is the same lesson as the HTTP-inside-a-transaction bug I removed from order-service last week —
  never hold a database connection across a network call.

- **Sent real email through Mailpit**, added `GET /api/notifications` (ADMIN only, read-only — the
  only writer is the consumer), a gateway route for `/api/notifications/**`, a Dockerfile, a
  compose service with its own Postgres, and health probes.

### Key takeaways

- **At-least-once delivery is not a Kafka detail, it is a design constraint on my code.** It is
  what forces the unique constraint and the PENDING/SENT ordering.
- **A uniqueness check in application code is a race; a unique constraint is a guarantee.**
- **Ordering of side effects is a decision**: which failure would I rather have, a duplicate email
  or a missing one? Answering that explicitly decides the code.

## Friday 2026-09-11 — Retries, poison pills, and a bug only the running stack could show me

### What I did

- **Split failures into transient and permanent**, which is what a retry policy actually is.
  SMTP down → retry at 1s, 2s, 4s. Malformed JSON or an event missing its product id → no retries
  at all, straight to the dead-letter topic. Retrying the same bytes that just failed to parse is
  pure waste.

- **Added the dead-letter topic `stock.low.DLT`**, plus a "parking lot" listener that logs the
  stored failure reason and increments a counter. Nothing is replayed automatically: a human reads
  the reason, fixes the cause, and re-publishes if needed.

- **Learned what a poison pill really costs — by removing the protection.** I took out the
  `ErrorHandlingDeserializer` and sent one malformed message. It did not only fail its own test:
  **an unrelated retry test failed too**, because Kafka reads a partition strictly in order and the
  unparseable record blocked everything behind it. One bad message would have stopped alerts for a
  third of the catalogue. That is the clearest demonstration of why a DLT exists that I could have
  asked for.

- **Wrote the tests on real infrastructure** (Testcontainers: real Postgres, real Kafka, a real SMTP
  server): happy path, duplicate delivery, transient failure retried then sent, persistent failure
  landing in the DLT with the row left PENDING for inspection, poison pill not blocking the
  partition, invalid event skipping retries, and a v2 event with unknown extra fields still being
  consumed (tolerant reader — adding a field is not a breaking change).

- **Exposed metrics** on `/actuator/prometheus`: consumer lag from the Kafka client, plus my own
  counters for notifications handled (sent vs duplicate) and dead letters.

- **Wired the rest of the plumbing**: k8s manifests for Kafka, Mailpit and notification-service
  (schema-validated, not yet applied to minikube), a manual-only CI workflow matching the others,
  the new service added to the test matrix, and the ECR repository declared in Terraform.

- **Ran the whole thing end to end on docker compose.** Placed a real order through the gateway:
  stock 7 → 4, one email in the Mailpit inbox. A second order (4 → 3) sent nothing. Re-publishing
  the exact same record was ignored as a duplicate. A malformed record landed in the DLT.

### Problems and how I resolved them

- **The tests were all green and the running stack still disagreed with me.** Kafka UI showed the
  consumer group as `stock-low-listener`, not `notification-service`. Cause:
  `@KafkaListener(id = "...")` silently uses the **id as the group id** unless you say otherwise.
  Nothing failed — but renaming that id later would have created a brand-new group that re-reads
  the topic from offset 0. Fixed with `idIsGroup = false`, and pinned with a test that asserts the
  group name.

- **The fix itself became the demonstration.** Restarting under the corrected group name did
  exactly what the bug would have done: it re-read the entire topic. Two events were re-delivered,
  the database recognised both, and **zero extra emails were sent**. The idempotency I had built
  the day before paid for itself the same afternoon.

### What I'm planning

- Get the branch reviewed and merged, then apply the k8s manifests on minikube and watch consumer
  lag in Grafana.
- Build the compensating side as a saga: `order.cancelled` releasing reserved stock.
- Re-drill the Kafka block cold — it was my weakest interview topic (8/20) and this week is now the
  story I answer it with.

### Key takeaways

- **A dead-letter topic is not a nicety.** Without it, one unprocessable record halts its whole
  partition — and it takes unrelated failures with it.
- **Retry policy = classifying failures.** Transient gets backoff, permanent gets parked. Treating
  them the same is either an outage or a lost message.
- **Mocks and green tests cannot see the wire.** Second week running, the bug that survived every
  test was found by looking at the real running system.
- **The gap that remains, stated honestly:** the commit and the Kafka send are still two writes. If
  the process dies between them the alert is lost. Acceptable for an alert; for money it would not
  be, and that is exactly where the Outbox pattern comes back.
