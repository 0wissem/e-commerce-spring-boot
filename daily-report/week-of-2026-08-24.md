## Monday 2026-08-24 — Shipping the enrichment branch, then the oversell bug

### What I did

- **Merged and shipped last week's work.** `feat/domain-enrichment` → `dev` with `--no-ff`, so the
  five commits stay visible as a branch in history rather than being flattened. Verified the merged
  state locally first — that mattered, because it was the first time the daily report and the code
  coexisted on one tree. **CI then confirmed 75 tests on a clean runner** (product 40, order 21,
  monolith 14), which was the outstanding verification from the previous week. Branch deleted with
  `-d`, so git checked there was nothing unmerged before removing it.

- **Found a bug the codebase had been carrying silently: ordering never touched stock.**
  `OrderService.create()` didn't decrement anything. You could order 1000 units of a product with 1
  in stock, forever, and the catalogue would never notice. There was also **no locking anywhere** in
  the project — no `@Version`, no `@Lock`, nothing. That combination is what made concurrency the
  obvious next track: it isn't an exercise, it's a live defect.

- **Put the invariant in the entity, not the service.** `Product.decrementStock(int)` refuses to
  drive stock below zero and throws `InsufficientStockException`. The service decides *when* to
  decrement; the entity decides whether it is allowed. A service-layer check can be bypassed by the
  next caller — an entity that cannot reach an invalid state cannot be bypassed at all. Backed it
  with a `CHECK (stock_quantity >= 0)` constraint, because under concurrency only the database can
  make that guarantee.

- **Mapped the refusal to 409, not 400.** The request was well-formed and the client did nothing
  wrong — the resource simply isn't in a state that allows it. A 400 would tell the client to fix
  its payload, which is misleading; 409 says "retry later or order fewer".

- **Wired stock reservation into order creation with a compensating action.** Stock lives in
  product-service, so the reservation crosses a service boundary and cannot join our transaction:
  a rollback in order-service does **not** put the units back. If line 3 fails after lines 1 and 2
  were reserved, those reservations are already committed in another database. So each successful
  reservation is recorded and explicitly released on failure.

- **Proved the oversell actually happens.** `LostUpdateTest` reproduces it at the SQL level with two
  raw connections: both read stock 10, both compute 10 − 1, both write 9. Two units sold, one
  deducted. That is a *lost update*, and at scale it is the oversell.

### Problems and how I resolved them

- **Nearly shipped "we added a lock" without ever seeing the bug.** My first concurrency test only
  proved the *fixed* behaviour — 20 threads, no oversell. That is an assertion about a mechanism
  nobody has watched fail. Added the unguarded reproduction so both halves exist: the bug, and the
  thing that stops it. A fix you cannot demonstrate the absence of is a fix you are trusting.

- **The compensating action can itself fail**, and that is not hypothetical. Every release is
  attempted independently and failures are logged rather than thrown — we are already unwinding one
  error, and letting a second escape would replace the real cause with a misleading one. Anything
  that fails there leaks stock, which is the honest limitation of a synchronous compensation: a
  production system would queue them for retry.

### What I'm planning

- Optimistic locking (`@Version`) and a retry policy, then pessimistic locking as a measured
  counterpart, then isolation levels — all against real Postgres.
- Then the transaction-boundary fix in `OrderService.create()` and the contract migrations that
  finally drop the legacy `double` money columns.

### Key takeaways

- **Invariants belong in the entity.** The service chooses when to act; the entity decides what is
  legal. Anything else is a rule with a bypass.
- **A cross-service write cannot be rolled back by `@Transactional`.** Once another service has
  committed, the only undo is an explicit compensating action — and it can fail too.
- **409 is "the resource says no", 400 is "your request is malformed".** Sending the wrong one
  sends the client debugging the wrong thing.
- **Demonstrate the bug, not only the fix.** Otherwise the safety of the mechanism is an article of
  faith.
